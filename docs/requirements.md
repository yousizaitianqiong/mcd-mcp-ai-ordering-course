# 编号化用户需求、用户故事与验收标准

> 项目：AI 麦乐送助手
> 文档用途：小组讨论、实现对照、课堂演示和最终报告取证
> 当前口径：Mock 是课堂稳定回退路径；在具备测试账号、配送地址和服务端凭据后，真实 MCP 联调必须至少完成一次真实待支付下单。

## 1. 项目目标与范围

本项目把“我想吃什么”转换为可解释、可确认的点餐流程：

~~~text
自然语言需求
  → 配送地址
  → 可配送门店
  → 菜单与餐品
  → 购物车
  → 核价
  → 人工确认
  → 待支付订单
  → 订单状态
~~~

首版交付以课程演示和可审查的接口边界为目标，不实现完整支付系统、商家后台、退款、发票、配送履约或多平台聚合。

## 4. 验收标准

| 编号 | 前置条件 | 操作 | 通过判据 | 证据 |
| --- | --- | --- | --- | --- |
| AC-001 | 默认 .env 使用 APP_MODE=mock。 | 启动服务并访问 /api/health。 | 返回 ok=true、mode=mock；页面显示“Mock 演示模式”。 | 健康检查响应、页面截图 |
| AC-002 | Mock 服务和页面已启动。 | 输入“我想吃麦香鸡套餐，先帮我看看当前菜单和门店”。 | 出现地址、门店、菜单和中文助手回复；工具轨迹可见。 | SSE 事件、页面录屏 |
| AC-003 | 已有会话和配送上下文。 | 选择门店、查看菜单并点击加入餐品。 | 购物车出现餐品；重复加入时数量合并；清空后购物车为空。 | 页面状态、请求响应 |
| AC-004 | 购物车至少有一件餐品。 | 点击“开始核价”或发送“请核价当前购物车”。 | 展示商品价、配送费、优惠、总价、地址、门店和 expiresAt。 | 报价卡片、SSE quote |
| AC-005 | 已产生有效报价。 | 在不点击确认按钮的情况下刷新页面或继续查询。 | 不产生订单，不调用 create-order。 | 服务端日志、数据文件、订单列表 |
| AC-006 | 已产生未过期报价。 | 点击“确认并创建待支付订单”。 | /api/orders/confirm 校验会话、报价哈希和有效期后只创建一次订单；页面进入待支付状态。 | 请求记录、订单卡片、审计事件 |
| AC-007 | 已创建 Mock 或真实待支付订单。 | 查看订单卡片并打开支付链接。 | 只展示待支付链接；应用不读取支付信息、不自动付款。 | 页面截图、演示记录 |
| AC-008 | 已创建订单。 | 点击刷新或发送“查询订单状态”。 | 返回对应订单状态；重复刷新不再次创建订单。 | 订单状态响应 |
| AC-009 | 已准备真实 MCP Token、在线模型、测试账号和配送地址。 | 以 APP_MODE=mcd 运行，完成地址、门店、菜单、优惠券和核价查询。 | /api/health 返回 mode=mcd；模型完成查询类工具调用；展示字段来自真实 Provider。 | 脱敏请求/响应、页面录屏 |
| AC-010 | 真实联调或 Mock 演示均可检查本地材料。 | 检查浏览器 Network/Source、服务端日志、.env 和 data/app-state.json。 | 找不到 Token、模型 Key、Authorization Header、支付信息和未脱敏个人信息。 | 脱敏检查清单 |
| AC-011 | 构造错误或服务异常。 | 分别触发空购物车、无效餐品、报价过期、重复确认、401、429、超时或无订单查询。 | 返回稳定错误码和中文提示；写操作失败时不自动重试。 | 错误响应、日志 |
| AC-012 | 代码和文档处于同一提交。 | 按 README、架构、分工和测试计划执行一次审查。 | 文档接口字段与源码一致；每项需求有负责人和验收证据位置。 | Review 清单、PR 记录 |

### 真实 MCP 的硬性联调门槛

真实联调不以“能读取 Token”作为完成标准，必须按以下顺序执行：

1. 由小组在仓库外确认测试账号、配送地址、支付/服务条款和操作人。
2. Token 和在线模型 Key 只写入本地服务端 .env，不写入命令历史、截图、Issue 或提交。
3. /api/health 明确返回 mode=mcd，并确认在线模型已配置。
4. 真实完成地址、门店、菜单、优惠券和核价查询，核对页面字段和 Provider 返回值。
5. 一名操作成员与一名复核成员共同核对地址、商品、金额和报价有效期。
6. 由操作成员在页面点击一次确认，获得真实待支付订单号；不自动支付。
7. 记录脱敏订单号、时间、状态和异常；清除或保护包含个人信息的本地数据。

如果任一前置条件缺失，状态写为“阻塞/待凭据”，不能以 Mock 结果替代真实联调结论。

## 5. 约束需求

- 项目为课程非商业用途，不实现完整支付系统、商家后台或多平台聚合。
- Token 只从服务端环境变量读取，不进入浏览器、数据库、日志、截图或 Git。
- 模型只能自动调用查询、购物车和核价工具；写操作不自动重试。
- 核价内容、会话归属和有效期必须在服务端复核，不能只相信浏览器传来的金额。
- 官方 MCP 不可用时使用显式标注的 Mock；不得把 Mock 订单包装成真实订单。
- 真实 create-order 具有外部副作用，必须使用批准的测试账号，由两名成员复核后执行一次。

## 6. 非目标

- 不代替用户输入或保存银行卡、支付密码、支付 Token。
- 不做真实配送履约、退款、发票和商家运营后台。
- 不把浏览器实验性 WebMCP 当作系统运行前提。
- 不在本 Issue 中新增 API、TypeScript 类型、数据库格式或自动化测试框架。
