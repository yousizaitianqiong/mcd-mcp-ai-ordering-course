# 四人小组分工与排期

小组人数按 4 人执行。每个人负责一个可独立验收的结果，同时通过冻结接口进行联调。

| 成员 | 负责模块 | 主要产出 | 联调接口 |
| --- | --- | --- | --- |
| 成员 A：需求与文档 | 用户访谈、编号需求、用例、架构图、演示脚本和最终报告 | `docs/requirements.md`、`docs/architecture.md`、演示记录 | 维护验收口径和需求变更表 |
| 成员 B：MCP 与模型后端 | Streamable HTTP MCP 客户端、官方 Provider、模型适配、工具白名单和确认流程 | `apps/server/src/mcp`、`providers/mcd.ts`、`model.ts`、`orchestrator.ts` | 对接 Provider 与 SSE 事件 |
| 成员 C：前端交互 | 聊天窗口、工具轨迹、地址/门店、菜单、购物车、报价确认和订单卡片 | `apps/web/src` | 消费 SSE 与 REST API，不读取密钥 |
| 成员 D：Mock、测试与集成 | Mock Provider、异常测试、端到端验证、部署说明和课堂联调 | `providers/mock.ts`、测试文件、`docs/test-plan.md` | 提供稳定演示数据和验收证据 |

## 建议排期（2–4 周）

### 第 1 周：冻结需求和最小闭环

- A 完成编号需求、用例和验收主流程。
- B 完成 `FoodOrderProvider`、MCP 客户端骨架和健康检查。
- C 完成页面布局、聊天输入和 Mock 数据展示占位。
- D 完成 Mock 菜单、报价和订单状态，以及基础测试脚手架。

### 第 2 周：完成联调

- B 接入 OpenAI 兼容模型和查询工具白名单。
- C 接通 SSE、菜单/购物车/确认卡片。
- D 补齐 401、429、超时、报价过期和重复确认测试。
- A 组织一次 Mock 演示并记录问题。

### 第 3–4 周：真实 MCP 小范围验证和交付

- 先验证地址、门店、菜单、优惠券和核价，不立即创建真实订单。
- 确认测试账号、地址和服务条款后，再由一名成员人工点击一次真实下单。
- A 整理调研矩阵、架构图、测试记录、分工表和演示脚本。
- 全组做一次无网络 Mock 演示，确保课堂现场有回退方案。

## 协作规则

- 不提交任何 Token、真实手机号、个人地址、支付链接或未脱敏 MCP 原始响应。
- 后端变更先补接口说明；前端不依赖 Provider 私有字段。
- `create-order` 相关变更必须由两名成员复核，并在测试记录中注明是否触发外部副作用。
