# 课堂演示脚本

## 1. 演示目标与总原则

本项目用一条可解释的业务链展示 AI 点餐：

~~~text
自然语言点餐 → 地址/门店 → 菜单 → 购物车 → 核价 → 人工确认 → 待支付订单 → 状态查询
~~~

课堂主流程使用 Mock，控制在 6–10 分钟；真实 MCP 片段必须在条件具备时执行，并以一次真实待支付下单作为联调终点。没有凭据、测试账号或网络时，必须明确记录为阻塞并切换到 Mock 运行，不把 Mock 结果说成真实结果。

## 2. 演示前检查

| 检查项 | Mock 路径 | 真实 MCP 路径 |
| --- | --- | --- |
| 运行模式 | APP_MODE=mock | APP_MODE=mcd |
| 服务 | Node 服务和 Vite 页面已启动 | Node 服务、Vite 页面、MCP 服务可访问 |
| 模型 | 可使用规则演示代理 | DeepSeek `deepseek-v4-flash`、普通 Tool Calls；变量均由服务端配置 |
| 凭据 | 不需要 | Token 只写入本地服务端 .env |
| 账号和地址 | 使用显式脱敏的 Mock 数据 | 使用小组批准的测试账号和配送地址 |
| 外部副作用 | 只生成模拟订单 | 允许一次真实待支付下单，不自动支付 |
| 复核人 | 演示者自检 | 一名操作成员 + 一名复核成员 |

建议预先执行 `pnpm build`、`pnpm test:mock`，并访问 `/api/health`。完整端口、环境变量和单机启动方式见[部署与联调说明](deployment.md)。演示前清理浏览器旧会话，避免上一轮报价或订单干扰本轮证据。

## 3.1 DeepSeek + Mock Provider 演示

这是无麦当劳 MCP Token 时的模型验收路径：保持 `APP_MODE=mock`，只在服务端 `.env` 配置 `MODEL_BASE_URL=https://api.deepseek.com`、`MODEL_API_KEY` 和 `MODEL_NAME=deepseek-v4-flash`。页面仍必须显示 Mock Provider；模型可以调用地址、门店、菜单、购物车和核价工具，但 `create-order` 只允许页面确认接口触发。记录 `/api/health` 的 `modelConfigured=true`、工具轨迹和报价哈希，不记录 Key 或 Authorization Header。

## 3. Mock 完整演示（6–10 分钟）

| 时间 | 演示者操作 | 页面和 SSE 预期 | 讲解重点 |
| --- | --- | --- | --- |
| 0:00–1:00 | 打开首页，指出顶部“Mock 演示模式”，访问 /api/health。 | 返回 mode=mock；页面显示规则演示代理。 | 外部 MCP 不可用时仍能复现课程闭环。 |
| 1:00–2:00 | 输入“我想吃麦香鸡套餐，先帮我看看当前菜单和门店”。 | 出现助手回复、地址、门店、菜单和工具轨迹；可见 session、tool、addresses、stores、menu。 | 模型或规则代理不能猜地址、门店编码和价格。 |
| 2:00–3:00 | 点击麦香鸡套餐“加入”，再重复点击一次；展示购物车。 | cart 出现餐品，数量合并为 2，商品小计更新；真实 MCP 有精确营养匹配时显示每份和合计热量，否则显示暂无数据。 | 购物车由服务端保存，热量只来自 Provider 的明确营养字段，不做估算。 |
| 3:00–4:00 | 点击“开始核价”，或发送“请核价当前购物车”。 | 出现 quote 和 confirmation_required；显示地址、门店、商品价、配送费、优惠、总价和有效期。 | 报价是确认依据，金额不能由模型自行编造。 |
| 4:00–5:00 | 不点击确认按钮，刷新页面或发送普通查询。 | 不产生订单；仍没有 order 事件或订单卡片。 | create-order 不在模型工具列表中，未获人工确认不得写入订单。 |
| 5:00–6:00 | 核对地址、餐品、数量和总价，点击“确认并创建待支付订单”。 | 出现 `MOCK-ORDER-*`、待支付（模拟）状态和保留域名 `.invalid` 模拟链接；购物车清空。 | 只有页面确认按钮进入 /api/orders/confirm；应用不会代付，也不要打开模拟链接。 |
| 6:00–7:00 | 点击“刷新”，再发送“查询订单状态”。 | 订单状态更新，不重复创建订单。 | 查询和创建是两条不同路径，刷新不产生新的写操作。 |
| 7:00–8:00 | 清空购物车或说明异常场景。 | 出现友好中文提示；可展示报价过期、空购物车、重复确认等预案。 | 错误要能解释下一步，不泄露下游凭据和原始敏感数据。 |

### Mock 讲解台词

> 这不是让模型直接替用户下单。模型负责理解需求和调用查询/核价工具；真正的创建订单被放在服务端人工确认闸门之后。课堂没有真实 Token 时，页面明确显示 Mock，订单也标注为模拟待支付订单。

## 4. 真实 MCP 受控演示

真实片段不替代 Mock 主流程，且必须满足以下前置条件：

- 小组已确认测试账号、配送地址、服务条款和允许的外部副作用。
- Token、在线模型 Key 和地址信息只保留在本地受控环境。
- 操作成员和复核成员在场。
- 已约定只创建一次待支付订单，不自动打开或完成支付。

| 顺序 | 操作 | 必须记录的结果 | 安全闸门 |
| --- | --- | --- | --- |
| 1 | 以 APP_MODE=mcd 启动服务并访问 /api/health。 | mode=mcd、provider=mcd、modelConfigured=true；响应不含 Token。 | 若模式不是 mcd，停止真实演示。 |
| 2 | 输入自然语言点餐需求。 | 真实模型产生查询类工具调用；页面展示 tool 轨迹。 | 只允许白名单工具，检查工具名和参数不含凭据。 |
| 3 | 查询地址、可配送门店、菜单和餐品详情。 | 页面字段与真实 Provider 返回值一致。 | 核对测试地址和门店，截图脱敏。 |
| 4 | 查询优惠券并发起核价。 | 展示真实商品价、配送费、优惠、总价和有效期。 | 复核人逐项核对地址、商品、金额和有效期。 |
| 5 | 操作成员点击一次“确认并创建待支付订单”。 | 返回真实外部订单号和待支付状态。 | 这是唯一一次真实 create-order；失败或未知状态不重试。 |
| 6 | 保存脱敏证据并结束。 | 记录时间、订单号后四位或其他脱敏标识、状态和错误。 | 不自动支付；清除或保护本地个人数据和响应文件。 |

真实订单状态查询不是本 Issue 的真实硬性终点；若服务条款和账号允许，可在不产生新写操作的前提下追加 query-order，并单独记录结果。

## 5. 失败回退与证据记录

真实服务出现 401、429、超时、网络错误、空地址、无门店、商品失效或报价过期时：

1. 停止真实写操作，不自动重试 create-order。
2. 在演示记录和最终报告中写明错误码、发生步骤、是否产生外部订单和当前状态。
3. 关闭或清理真实凭据环境。
4. 重新以 `APP_MODE=mock` 启动，并以 `/api/health` 确认 `provider=mock`，再完成 Mock 主流程。
5. 将真实路径标记为“阻塞/部分完成”，不能用 Mock 证据替代真实联调证据。

每次演示至少保留以下脱敏证据：

| 证据 | 内容 | 禁止内容 |
| --- | --- | --- |
| 健康检查 | mode、provider、modelConfigured、协议版本 | Token、Key、Authorization Header |
| 页面截图/录屏 | 工具轨迹、菜单、报价、确认闸门、订单状态 | 真实地址、手机号、完整支付链接 |
| 请求摘要 | 路由、状态码、错误码、时间 | 请求头凭据、完整个人信息 |
| 订单记录 | Mock 订单号或真实订单脱敏标识、状态 | 支付密码、银行卡信息 |
