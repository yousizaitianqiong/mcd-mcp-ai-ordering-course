# 编号化用户需求与验收标准

教师文件的“编号化用户需求列表”格式作为文档参考；以下编号是本项目自定义需求，面向四人小组的 AI 麦乐送助手，不继承教师示例中的聊天工具功能约束。

## 用户需求

| 编号 | 需求 | 验收条件 | 优先级 |
| --- | --- | --- | --- |
| MCD-USR-0001 | 用户可以用自然语言描述想吃的餐品、数量、预算或优惠需求 | 聊天区接受文本，返回中文助手回复；无模型时可在 Mock 模式完成演示 | P0 |
| MCD-USR-0002 | 用户可以查看配送地址并选择可配送门店 | 页面展示地址和门店，选择后显示当前上下文 | P0 |
| MCD-USR-0003 | 用户可以查看当前门店菜单和餐品详情 | 页面显示餐品名称、价格、标签和加入购物车按钮 | P0 |
| MCD-USR-0004 | 用户可以维护购物车 | 支持加入餐品、数量合并、查看小计和清空购物车 | P0 |
| MCD-USR-0005 | 用户可以发起核价 | 服务端使用当前地址、门店和购物车调用 Provider，返回商品价、配送费、优惠、总价和有效期 | P0 |
| MCD-USR-0006 | 创建订单必须人工确认 | 模型没有 `create-order` 工具；只有点击页面确认按钮才请求 `/api/orders/confirm` | P0 |
| MCD-USR-0007 | 用户可以获得待支付链接并查看订单状态 | 成功创建后展示订单号、状态和支付链接；支付由用户自行完成 | P0 |
| MCD-USR-0008 | 无 Token 或官方服务不可用时可以完成课程演示 | `/api/health` 明确返回 `mock`，页面显示 Mock 演示模式 | P0 |
| MCD-USR-0009 | 用户不应看到服务端密钥或支付信息 | 浏览器响应、源代码和日志中不得出现 MCP Token / 模型 Key；服务端不保存支付信息 | P0 |
| MCD-USR-0010 | 用户可以理解工具调用过程 | 页面展示查询地址、门店、菜单、核价等工具的运行状态 | P1 |
| MCD-USR-0011 | 用户可以看到友好的异常提示 | 覆盖未配置、401、429、超时、空地址、无门店、商品失效、报价过期等错误 | P1 |
| MCD-USR-0012 | 小组成员可以按接口契约并行开发 | Provider、ModelAdapter、HTTP API 和前端事件结构写入架构文档 | P1 |

## 约束需求

- 项目为课程非商业用途，不实现完整支付系统、商家后台或多平台聚合。
- Token 只从服务端环境变量读取，不进浏览器、数据库或日志。
- 模型只能自动调用查询和核价工具；写操作不自动重试。
- 核价内容、会话归属和有效期必须在服务端复核，不能只相信浏览器传来的金额。
- 官方 MCP 不可用时只能切换为显式标注的 Mock，不能把 Mock 订单包装成真实订单。

## 验收主流程

```text
自然语言点餐
  → 查询地址
  → 查询可配送门店
  → 查询菜单 / 加入购物车
  → 核价并展示有效期
  → 用户确认
  → 创建待支付订单
  → 查询订单状态
```

## 非目标

- 不代替用户输入或保存银行卡、支付密码、支付 Token。
- 不做真实配送履约、退款、发票和商家运营后台。
- 不把浏览器实验性 WebMCP 当作系统运行前提。
